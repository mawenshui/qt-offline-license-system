# 开发全流程

本文定义从需求进入到 GitHub Release 的完整流程。具体协议和密码学约束以《Qt 离线授权系统详细设计》和《安全边界与运维指南》为准。

## 1. 流程总览

```text
需求/缺陷
  → 明确验收条件和安全边界
  → 建分支
  → 最小实现与测试
  → 本地 Release 构建
  → 核心测试 + 真实进程测试
  → 文档与兼容性复核
  → Pull Request / CI
  → 合并 main
  → 打标签
  → 可复现打包、校验、Release
  → 发布后冒烟与回滚观察
```

## 2. 需求与设计

每项变更先记录：

- 用户问题、目标行为和明确不做的范围。
- 可执行验收条件。
- 是否改变授权容器、载荷、密钥库、批量输入或运行状态格式。
- Windows/Linux、Qt 5/Qt 6、32/64 位兼容影响。
- 私钥、产品密钥、硬件标识和客户数据的处理方式。

涉及协议、密码学、信任根、时间状态或防回滚逻辑时，必须先更新详细设计并给出向后兼容/迁移方案。禁止用自研密码算法替代 libsodium。

## 3. 分支和提交

- `main`：始终保持可构建、可测试、可发布。
- `feature/<name>`：功能。
- `fix/<name>`：缺陷或安全修复。
- `docs/<name>`：纯文档。
- `release/<version>`：仅在需要稳定发布候选时使用。

提交应小而完整，格式建议为 `type(scope): summary`，例如：

```text
feat(collector): show friendly hardware names
fix(runtime): reject rolled-back state sequence
docs(release): document Windows packaging
```

不得提交 `.qtkv`、`.qtlic`、`.qreq`、导出的运行端密钥配置、客户数据、构建目录或 IDE 用户配置。

## 4. 开发环境

### Windows

- Qt 5.12.12 或后续版本，MinGW 32/64 位。
- qmake、`mingw32-make`、PowerShell 5+。
- 仓库内相同架构的 libsodium 预编译包。

```powershell
git clone https://github.com/mawenshui/qt-offline-license-system.git
New-Item -ItemType Directory build-license-system | Out-Null
Set-Location build-license-system
qmake ..\qt-offline-license-system\LicenseSystem.pro CONFIG+=release
mingw32-make -j4
```

### Linux

- Qt 5/6 开发包、qmake、C++14 编译器、`pkg-config`、`libsodium-dev`。

```bash
sudo apt-get install build-essential qtbase5-dev qt5-qmake libsodium-dev
mkdir build-license-system && cd build-license-system
qmake ../qt-offline-license-system/LicenseSystem.pro CONFIG+=release
make -j"$(nproc)"
```

使用源码目录外的 shadow build。不要把生成文件混入仓库。

## 5. 实现规则

- 优先复用 `core/` 的类型、校验和序列化逻辑，修复共享根因。
- GUI 只负责输入和展示，不能复制协议或密码学判断。
- 面向用户的配置名称使用易懂中文；内部键通过 Tooltip、完整技术数据页或文档提供。
- 文件解析设上限，所有密码学和状态异常 fail closed。
- 日志不得输出密钥、口令、原始硬件序列号或完整解密载荷。
- 新增非平凡逻辑时，在 `tests/main.cpp` 增加一个可运行断言；跨进程流程写入 `tests/real_world_cli.ps1`。

## 6. 验证矩阵

每次提交至少完成：

1. `qmake` + Release 全量构建。
2. `bin/license-core-tests.exe` 核心断言。
3. 改动涉及 GUI 时启动签发器和采集器，确认进入事件循环。
4. 改动涉及硬件、文件格式、CLI、密钥库或 Runtime 时执行真实进程测试。
5. `git status` 检查没有密钥或客户文件。

发布前还需验证：

- 新建密钥库、导出运行端配置。
- 采集请求、单个签发、批量签发、读取和完整验证。
- 篡改签名/密文拒绝。
- 硬件不匹配、未生效、过期、额度耗尽和状态回滚拒绝。
- Release 解压到干净目录后可启动，不依赖开发机 PATH。

## 7. 代码审查

Pull Request 描述必须包含：

- 行为变化和用户可见结果。
- 安全、协议和兼容影响。
- 测试命令及结果。
- 文档是否同步。

密码学、密钥、授权格式、时间状态和防回滚修改至少需要一次独立安全审查。CI 通过不能替代人工审查。

## 8. 版本与发布

使用语义化版本：

- MAJOR：不兼容的协议/API/状态变化。
- MINOR：向后兼容功能。
- PATCH：向后兼容修复。

发布步骤：

1. 更新 `CHANGELOG.md` 和受影响文档。
2. 从干净 `main` 做 Release 构建并运行完整验证矩阵。
3. 执行 `scripts/package-release.ps1 -Version X.Y.Z`。
4. 校验 `dist/SHA256SUMS.txt`，抽样解压并启动应用。
5. 创建带注释标签 `vX.Y.Z`。
6. 创建 GitHub Release，上传两个 ZIP 和校验文件。
7. 在干净 Windows x64 机器完成发布后冒烟。

脚本生成：

- `qt-offline-license-system-vX.Y.Z-windows-x64.zip`
- `qt-offline-license-runtime-sdk-vX.Y.Z.zip`
- `SHA256SUMS.txt`

## 9. 回滚与热修复

- Release 资产不可静默替换。发现问题时标记受影响版本，不复用旧标签。
- 无数据格式变化：从上一稳定标签建 `fix/` 分支，修复后发布新 PATCH。
- 有授权/状态格式变化：先提供兼容读取或迁移工具；禁止直接删除客户状态文件。
- 有密钥泄漏：立即停止签发、撤销/轮换签名链和产品密钥，发布安全公告并重新授权。
- 回滚后继续保留失败资产的校验值、测试证据和原因，便于审计。

## 10. 完成定义

变更只有在以下条件都满足时才算完成：代码与文档一致、测试通过、无敏感文件、兼容影响明确、Release 可独立运行、校验值已发布、回滚路径可执行。
